## 5. Troubleshooting with limited AI assistance

### 5.1 Empty `BASE_URL` in GitHub Actions

One CI run failed because the application URL was empty. The workflow
referenced a repository variable that had not been configured correctly.

I investigated the GitHub repository settings and corrected the variable
configuration. The issue also highlighted the difference between using
`??` and `||` when an environment variable is an empty string.

AI assistance was limited to explaining the error and pointing me
towards the relevant behaviour. I made and verified the correction.

### 5.2 Checking the correct artefact

At one point, I downloaded an artefact from an earlier workflow run. Its
error context did not correspond to the latest failure, which initially
made the result confusing.

I checked the workflow run and downloaded the artefact from the correct
run. This reinforced the importance of matching artefacts to the exact
GitHub Actions run being investigated.

### 5.3 Cloudflare verification in GitHub Actions

The most significant issue I asked AI about was Cloudflare bot
protection.

**Problem:** GitHub Actions runners sometimes received a Cloudflare page
asking the visitor to verify that they were human, instead of receiving
the application.

I asked whether the challenge could be bypassed and whether adding waits
between tests, reducing requests, or handling browser contexts
differently could help.

The discussion suggested that the challenge could be related to the
reputation of datacenter IP addresses and the pattern of requests. It
also clarified that clearing browser contexts would not necessarily
help, because it removes session state and does not change the runner's
IP reputation.

I then investigated the test flow and made the changes myself:

  ----------------------------------------------------------------------------
  File                                     Change
  ---------------------------------------- -----------------------------------
  `tests/helpers/create-test-account.ts`   Removed an unnecessary login-page
                                           reload after registration

  `pages/ForgotPasswordPage.ts`            Avoided unnecessary full-page
                                           navigation when the application was
                                           already open

  `pages/ComparePage.ts`                   Used the application's Home link
                                           instead of navigating to the root
                                           URL again

  `pages/PurchasePage.ts`                  Used application links and the cart
                                           icon instead of repeated full-page
                                           navigations

  `playwright.config.ts`                   Reduced CI workers from 2 to 1

  `fixtures/pages.fixture.ts`              Added handling to identify and
                                           label failures caused by the
                                           Cloudflare challenge

  `fixtures/pages.fixture.ts`              Added a 3-second pause before each
                                           CI test and a 15-second pause
                                           before a retry
  ----------------------------------------------------------------------------

The AI helped me understand the possible causes and how a delay could be
configured. I applied and tested the changes in the project.

The navigation changes reduced the number of full-page navigation call
sites from 8 to 4. Each test now makes only one initial full-page load
where possible, using client-side application navigation afterwards.

**Verification:** I ran the full suite in CI mode and got 9 passing
tests. I also tested the Cloudflare detection logic with a temporary
test that simulated the verification page, then removed that temporary
test.

Adding pauses increased the local CI-mode test duration from
approximately 39 seconds to 1.6 minutes. These changes reduced
unnecessary requests but could not guarantee that Cloudflare would never
challenge the runner.

I did not use CAPTCHA-solving services or stealth plugins to circumvent
the site's protection. A more reliable approach would be to run the
application locally in the pipeline using its Docker Compose setup and
set `BASE_URL` to `http://localhost:4200`.

## 6. Sharding and performance considerations

The pipeline uses four shards, but the test suite currently contains
only nine tests. Each shard has its own setup cost, including checkout,
dependency installation, and browser installation. Therefore, four
shards do not necessarily make this small suite faster.

I treated sharding as an implementation requirement and measured the
actual GitHub Actions performance rather than assuming it would provide
a fourfold speed improvement. The measured results were recorded in the
README.
